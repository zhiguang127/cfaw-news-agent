# 汇率契约

执行检查在 `fx.splash`。汇率是**第四个平行子系统**：和天气、节假日一样，它有自己的
契约、自己的缓存和存储，只共用宿主和 HTTP 层，不进 `news_record`。

理由和天气一样：汇率没有发布时间，只有生效日期。把它塞进 `sources.json` 只会让
`timestamp_kind` 变成一句谎话。它也不是新闻——它每天都变，但变的不是"发生了什么"。

## 只服务出国子场景

汇率对绝大多数日程没有意义。查一次北京天气会影响要不要带伞；查一次美元兑人民币
不会影响任何日程，除非这趟行程要花钱 abroad。因此货币列表是**调用方传进来的参数**
（`fx_movers(currencies)`），不是数据层自己维护的可变状态——哪个币种重要是产品决策，
数据层只负责算。上限 `fx_max_currencies = 8`：超了直接返回空，不做截断，因为悄悄
丢掉一个币种比明确拒绝更坏。

当前支持集合 `fx_supported_currencies`：`cny usd eur jpy krw gbp chf aud cad thb sgd hkd nzd`。
这是明确维护的出行币种集合，**不是完整 ISO 4217 目录**。其他代码返回无数据，包括
`btc`、`eth`、`sol`；新增币种需同时更新集合和固定检查。

## 报价方向

按 **1 CNY 等于多少外币** 报，不是反过来。这样"100 块能换多少日元"不需要调用方做
除法——把乘法搞反是这类接口最常见的错误来源，而它是静默的。

`fawazahmed0/exchange-api` 的文件结构是 `{date, cny: {<code>: <amount>}}`，一个文件
覆盖全部币种。所以跟踪 N 个币种仍然是一天一次请求，不随 N 增长。

## 变动的三态

`change_ratio` 和 `previous_per_cny` 在**没有更早一天可比时为 `nil`**，不是 0。

| `per_cny` | `change_ratio` | 含义 |
| --- | --- | --- |
| 数字 | 数字 | 有可比日，变动量已知（可正可负） |
| 数字 | `nil` | 有汇率，但只有一个观测点，**是否变动未知** |
| `nil` | `nil` | 没有这个币种的数据 |

仅有一个可用牌价日时属于第二行；首次加载三日窗口也可能已获得可比日。
契约禁止把未知报成 `change_ratio: 0`——0 是一个真实
的、可上报的观测值（汇率一整天没动），把它当成"没有可比日"的占位符，就会在汇率
陈旧时给出"汇率平稳"的假安心。

`fx_record_valid` 会拒绝 `change_ratio` 有值而 `previous_per_cny` 为 `nil` 的记录：
变动量没有分母就不该存在。

## 阈值是产品决定，不是数据事实

`fx_alert_change_ratio = 0.02`。汇率每天都小幅波动，不设阈值用户会被刷屏。

固定 fixture（2026-10-01 对比 2026-09-30）中，日元约 +0.75%、美元约 -0.002%、
韩元约 +0.19%；测试选定的 `usd/jpy/eur/krw` 都没有越过 2%，因此这组输入的
`fx_movers` 返回空数组。这只验证固定日期数据，不代表运行当天行情或所有币种。

阈值之上才返回 `{currency, known, change_ratio, per_cny, rate_date}`。
`known: false` 表示无可比日，`change_ratio: nil`，同样不是 0。

## 上游结构与归一化

上游文件混着加密货币代码（`1inch`、`aave`、`btc`、`eth`、`sol`），它们和法币代码
在同一个 map 里。三字母正则不能区分这两类数据。`fx_amount` 在每次读取时检查
支持集合和正数，所以这些加密资产不会进入出行建议路径。

代码只**校验**不做大小写折叠：运行时没有字符串小写方法，而悄悄改写用户输入比拒绝
它更糟。`fx_rate("US")` 返回无数据，不返回 `usd` 的汇率。

上游日期必须与请求的日期一致（`fx_table_from_upstream` 的第三个参数），防止 CDN
把旧文件当新文件返回，那种情况会让 `change_ratio` 变成 0 而不是未知。

## 排序按时间戳，不按字符串

`fx_ingest` 用 `weather_time_stamp(day)` 的数值比较维护"最新日/最近的较早可用日"。
较早的响应晚到时也更新比较日；三天响应的六种排列结果一致。同日替换只更新该日
汇率，不能把两次同日观测当作跨日变动。无论是否跳过缺失日，都保留真实牌价日。
直接比较日期字符串在这个运行时里**永远返回 false**（见
`docs/splash-runtime-notes.md`），ISO 日期字典序正确这件事反而让这个 bug 极难发现。

## 缓存与许可

每个日期一份 `fx_v1_cny_<date>.json`。常规 `fx_load(today)` 先恢复整个三日窗口的
缓存，再请求缺失日期；`fx_load_from(today, days)` 只接受 1–3 的整数天数。缓存必须
匹配文件名中的日期和 `cny` 基准，`fetched_at` 保留原取回时刻，不改成 0 或当前时钟。

`fx_status_by_date[day]` 为 `{state, error, cache_error}`，`state` 是
`not_loaded / loading / cached / fresh / error`。`fx_pending` 表示进行中的请求数。
`fx_status` 汇总已有日期的失败和缓存异常；某日成功不会清除另一日期的错误。
缓存异常在重新获取并成功保存该日后清除；网络失败仍可手动重试。
状态为空只能说明没有记录的错误，判断变动仍须检查 `fx_pending`、牌价日期和
`fx_rate()` 的 nil 字段，不能把未加载状态报成"汇率平稳"。

同日期加载中不会重复请求；每个请求的标识拒绝重复回调和 `fx_reset()` 后的旧完成。
`fx_reset()` 清除内存状态，不删除缓存，也不取消宿主已经发出的 HTTP 请求。
请求边界 `fx_http_request(url, redirects, callback)` 默认调用共享 HTTP 层，固定测试
替换此函数变量以回放成功、失败、乱序和重复完成，不发起真实请求。

许可字符串 `fawazahmed0/exchange-api, not central bank data` 必须随数据一起展示：
这不是央行中间价，把它当官方牌价呈现是误导。

## 还没做的

汇率只影响"这趟行程花多少钱"，不影响"这趟行程该不该改期"。它目前是独立子系统，
**尚未接入日程冲突判断**——`holiday_event_conflict` 那一套还没有 `fx_event_conflict`
对应物。接入的前提是行程记录里确实有目的地和币种，目前没有。

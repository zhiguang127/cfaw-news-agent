## 1. 交付目标与顺序

最终交付两个一级页面“首页 / 我的计划”，统一意图入口展开输入面板，与唯一的新闻搜索框区分。关注从自然语言创建，相关报道优先排在同一条新闻流前面，Agent 解释关注原因和日程影响；计划通过输入创建、补充和修改，移除日程表单。相关新信息可以产生待确认建议，用户决定后更新对应记录。

按最新讨论先完成首页适配，让后续输入和卡片有明确位置。H0 复用现有数据，不依赖新的模型结果契约；其余阶段按依赖推进：

| 阶段 | 工作 | 用户能看到的结果 | 依赖 |
| --- | --- | --- | --- |
| H0 | 首页结构适配 | 顶部两页切换、相关报道优先、条目内关联提示、菜单关注/收藏、唯一搜索框；保留天气 | 复用现有实现；本轮交付 |
| P0 | 核对运行基线、模型调用与已知缺口 | 后续开发有可复现的运行和测试依据 | 无 |
| P1 | 计划/关注契约、持久化和共用 Octos 请求边界 | 为输入和卡片提供真实数据与可靠状态 | P0 |
| P2 | 两页导航、统一输入与无表单计划流程 | 输入想法、补充信息、确认计划、继续输入修改 | P1 |
| P3 | 自然语言关注、候选召回与自动关联分析 | 保存关注后，刷新得到优先排列、带解释的相关新闻 | P1、P2 |
| P4 | 新闻与计划关联、建议确认与历史 | 新信息影响具体计划，用户确认后调整 | P2、P3 |
| P5 | 实际 Rinx 验收、性能回归与本地交付 | 两条输入流程及计划建议可演示，边界清楚 | P2–P4 |

P2 完成后有第一份可用交付：无表单的“我的计划”。P3 完成后具备初赛优先演示的两条流程。P4 和 P5 完成后覆盖设计中的新闻影响计划闭环。

### H0 本轮范围

- [x] 将四个底部标签收为顶部“首页 / 日程”，收藏和关注列表可从菜单进入。
- [x] 不另建关注框，筛选后将关注匹配或有当前 Agent 建议的报道优先排列；同组保留原时间顺序，不重复新闻。
- [x] 移除重复关键词框，将唯一的新闻搜索框放在页面底部；关注仍从菜单管理。
- [x] 条目下最多一行关联提示：规则匹配与 Agent 解释明确区分，日程影响点击进入证据/建议详情。
- [x] 切页保留分类与搜索；查看新闻后更新未读状态。
- [x] 分批预计算匹配与已保存的当前 Agent 提示，绘制读取结果；输入变化丢弃旧批次，过期或已处理建议不重复作为当前提示。
- [x] 保留右上角天气组件、选城、预报页及其独立加载。

H0 复用已保存且验证过的单条分析，不增加自动模型调用；日程页仍使用原有表单。P2 接入完整意图输入和计划卡，P3 将自动分析结果继续呈现在新闻条目下；不将 H0 标为 P2/P3 全部完成，也不重新引入首页关注框。

本计划按可验收成果拆分，不预设比赛截止日或承诺开发天数。真实模型与宿主表现先在 P0 检查，避免到交付时才发现接口或运行问题。

## 2. 需要复用和处理的基础

| 代码基础 | 实施判断 |
| --- | --- |
| 新闻抓取、规范化、缓存、去重、分类、收藏 | 复用，避免随页面改造重写数据链路 |
| 关注的来源/主题/关键词规则 | 作为词法召回基础；新增保存原话、偏好和多个规则的关注专题 |
| 日程持久化、版本检查、时间/冲突判断、完成/取消 | 复用；另增允许日期和时间未知的计划记录 |
| Octos 打开、请求、中断和超时保护 | 提取实际共用部分；现有执行器和 UI/新闻状态耦合，不能直接当作通用输入执行器 |
| 建议历史、忽略、替代、撤回与确认恢复 | 保留已有机制，再加入计划/专题关联和兼容路径 |
| 合并重绘、分批工作、GC 与 Windows 宿主修补 | 保留，并在新布局下回归；不得通过增大堆限制掩盖新问题 |

代码核对出的具体约束：

- `schedules.splash` 拒绝缺失或无效的起止时间；模糊计划不能直接写进现有日程。
- `analysis_start(row)` 以新闻 ID 和新闻证据构造请求；用户提出计划时没有新闻证据，需要独立的意图结果契约。
- 现有建议校验要求非空 `interest_ids`；只有计划、没有关注规则时的建议不能靠伪造兴趣来通过，需要调整契约和校验。
- H0 已保留 `select_page()` 的分类与搜索状态，仍不能直接读写滚动位置；新输入/计划页须继续保留列表实例并在宿主验证。
- H0 已将现有关注匹配移出新闻绘制回调，追加“240 条新闻 + 1 个主题 + 10 个关键词”回归。新专题还需按工作量扩展分批与缓存失效机制。

## 4. P1：记录、契约与执行边界

### 4.1 计划与关注记录

- [ ] 定义计划记录：稳定 `plan_id`、单调版本、用户原话、整理后的标题/地点、可为空的日期范围、状态，以及关联的具体日程 ID。
- [ ] 区分想法草稿、已确认计划和精确时间安排。日期范围明确即可确认计划；生成具体日程需要准确起止时间和用户确认。
- [ ] 定义关注专题：稳定 `topic_id`、版本、用户原话、范围偏好、启用状态和召回规则。保留现有 `interest_id` 规则作为兼容输入。
- [ ] 定义主题总结缓存：专题/配置/提示词版本、证据 ID 与内容版本、上次成功总结、成功时间和本次检查状态。
- [ ] 对用户记录、草稿和可丢弃缓存分别定义持久化方式、schema 版本、容量和错误含义。
- [ ] 旧关注继续可用，旧日程通过兼容视图出现在计划列表，保留原 ID 与状态；不强行归并旧关键词或虚构用户原话。
- [ ] 复用备份与保留坏文件的恢复策略，检查新增文件写入失败、部分写入及重启恢复。

建议新增独立模块，最终路径在本阶段确认，例如 `contracts/plans.splash`、`contracts/topics.splash`、`data/storage/plans.splash`、`data/storage/topics.splash`。增加模块时同步组装顺序，不能假设 bundle 能执行新的外部语言模块。

### 4.2 共用请求与分开校验

- [ ] 将现有真正共用的 Octos 请求、取消、超时和关联逻辑放到 `agent/runtime/` 的执行边界，UI 结果交由 `app/` 路由。
- [ ] 沿用一个应用 Agent，同一时刻只执行一个宿主推理任务。用户输入优先于自动汇总；需要中断时等待确认，不能并发复用当前中断接口。
- [ ] 请求携带应用生成的任务 ID、任务类型、对象 ID/版本与快照指纹。旧完成、重复完成和对象变化后的结果不得写入新状态。
- [ ] 分别定义“意图整理”“关注汇总”“新闻影响计划”结果，不让新计划套用必须引用新闻证据的旧校验器。
- [ ] 意图结果只形成草稿或待确认变更；关注汇总必须引用实际候选；日程动作校验版本、时间、许可与冲突。
- [ ] 统一可执行提示词的维护方式，保存在 `agent/prompts/`，由组装流程按目标 OctoScript 支持的方式生成/加载，记录提示词 revision。
- [ ] 在配置模块集中设置输入长度、追问上下文、候选数量、单次请求大小、超时、重试和自动汇总工作上限。

### 完成条件

固定输入能验证记录和三类结果的合法/非法情况。旧用户数据仍可读取；未知时间为未知。真实输入与新闻任务共用宿主生命周期保护，取消和迟到结果不污染新任务。请求超限减少完整记录或明确失败，不能截断 JSON。

主要涉及：[记录存储](../src/data/storage/records.splash)、[日程存储](../src/data/storage/schedules.splash)、[时间转换](../src/data/storage/schedule_time.splash)、[分析适配器](../src/agent/runtime/analysis.splash)、[结果校验](../src/agent/results/validator.splash)、[组装脚本](../scripts/assemble.py)。

### 5.2 输入到计划卡

- [ ] 用户提交一句计划后保存原话草稿，再调用意图整理，展示已知信息与待确定内容。
- [ ] 使用输入时的基准日期和用户时区解释相对日期；卡片展示具体年月日。有歧义时追问，不默认活动时间或时长。
- [ ] 一次追问解决一个关键缺口；用户可以离开，重开后继续补充草稿。
- [ ] 展示结果后通过“保存计划/保存安排”确认。只有明确的时间安排进入日程存储，并复用冲突和版本检查。
- [ ] 从计划详情输入“改成周五出发”“加一个西湖散步”，展示变更范围，再确认保存。
- [ ] 保留完成、取消等直接操作。AI 不可用时保留未处理草稿和错误原因，已有计划和新闻仍可查看。
- [ ] 新流程通过后移除日程表单、字段草稿状态和专用 UI 处理函数；保留仍被使用的存储与时间校验。

用户明确提出修改，与 Agent 根据新闻主动提出改期分别记录。明确修改在确认后走用户编辑路径；不能把它错误地套入默认关闭的主动改期许可。主动建议的许可仍在 P4 处理。

### 完成条件

用户可以仅通过输入创建、补充和修改计划，全程无录入表单。“下周去杭州两天”能形成草稿；“周六去周日回”能形成日期范围计划而不虚构出发时刻。切页、重启、模型失败和写入失败均不丢失已保存内容；重复确认不重复新增日程。

主要涉及：[应用视图](../src/frontend/app_view.splash)、[菜单](../src/frontend/components/menu.splash)、[现有日程页](../src/frontend/pages/schedule.splash)、[控制器](../src/app/controller.splash)、[启动](../src/app/startup.splash)。输入面板和计划卡作为可复用组件新增，计划操作放入独立应用模块，避免全部堆进控制器。

## 6. P3：关注输入与新闻关联分析

### 6.1 关注整理与召回

- [ ] 接通“关注 AI Agent 开发工具，少看融资新闻”等输入，展示范围与偏好，确认后保存专题。
- [ ] 接通自然语言修改、暂停和取消关注；来源关注、旧规则和专题使用明确的关联与状态。
- [ ] 复用词法召回，支持专题内多个关键词/来源/主题规则；明确组合方式、候选上限与确定性排序，不把所有同类新闻都判为相关。
- [ ] 预计算新闻与规则/专题的匹配结果，按时间片分批完成。绘制回调只读取结果，避免逐条重复扫描所有规则。
- [ ] 对规则修改、来源切换和新闻变化正确失效缓存；不要由“已读”决定是否值得分析。

### 6.2 汇总、缓存和触发

- [ ] 为相关报道构造真实关注与计划上下文，让 Agent 解释新闻变化、关注原因、具体日程影响与不确定性；跨报道总结放到详情，不另建首页关注区。
- [ ] 独立校验总结和来源引用，不要求兴趣总结必须产生计划动作。标题/摘要仍明确标为实际证据范围。
- [ ] 以意图版本、候选内容版本、提示词/配置版本和相关决定构造工作指纹；成功后保存，失败不能标为已经处理。
- [ ] 在关注保存、缓存恢复完成和新闻刷新完成后调度有限检查。刷新各来源的中间回调不反复调用模型。
- [ ] 合并重复检查，限制每轮专题/候选数量；超出时保持待检查状态，用户输入可优先执行。
- [ ] 提供有更新、无新增、未分析、证据不足、服务失败和旧缓存状态。重试有次数/间隔约束，避免每次重绘自动重试。

### 6.3 同一新闻流中的展示

- [x] 首页在现有新闻流内优先排列相关报道；条目下最多一行提示，不另建关注框。
- [ ] 接入自动分析产生的关联提示；同一报道更新原条目，保留必要的前次结果和变化。
- [ ] 详情展示原始意图、完整总结、候选覆盖与来源；修改关注后说明旧总结需要更新。
- [x] 旧规则只有匹配时说明关键词/主题/来源，不冒充已经生成 Agent 结论。

### 完成条件

“输入关注 → 保存 → 刷新 → 相关新闻优先并解释关系 → 查看来源 → 修改/暂停”可完整运行。重复新闻不重复分析；缺日期和矛盾报道不生成确定事实。服务失败保留历史与真实时间，不将过期结果呈现为当前影响。240 条新闻和多关键词的绘制超限回归通过，32 MiB 堆限制保留；首屏仍能看到多条普通新闻，首页只有一个搜索框。

主要涉及：[关注匹配](../src/data/retrieval/interests.splash)、[新闻列表](../src/frontend/components/news_list.splash)、[现有跟踪页](../src/frontend/pages/tracking.splash)、[首页](../src/frontend/pages/feed.splash)、[刷新控制器](../src/app/controller.splash)。新增专题汇总结果与缓存模块，替换通过后移除独立跟踪标签及失效的旧分析入口。

## 7. P4：新闻影响计划与建议确认

### 工作

- [ ] 依据计划地点、用户内容、日期范围和关联日程进行有限候选召回，避免仅以整个日程标题匹配新闻。
- [ ] 调整上下文与结果契约：支持只有计划而没有关注规则的情况；允许明确的计划/日程目标引用，拒绝未知或不一致引用。
- [ ] 兼容现有分析、建议和用户决定记录，记录新格式版本，不重置历史或把旧建议全部重新弹出。
- [ ] 建议区分计划层面的提醒与可执行日程动作。日期/时刻不明确时可解释影响，但不生成确定改期。
- [ ] 首页待处理入口与计划详情读取同一建议记录，显示对应计划、具体变化、证据、动作预览和不确定性。
- [ ] 主动改期继续默认关闭。用户可通过明确操作或输入允许对指定安排提出改期建议，仍不等于允许自动执行。
- [ ] 确认前重读计划/日程版本，复核证据新鲜度、许可和冲突。用户先修改计划后，旧建议失效并显示原因。
- [ ] 扩展既有同目标同证据抑制、忽略、替代与撤回机制；跨报道归并保留来源和限制，不把重复报道计为独立佐证。
- [ ] 多文件确认有稳定操作标识，处理日程已写但计划关联/决定保存失败的重试；不能将部分成功显示为全部保存。

### 完成条件

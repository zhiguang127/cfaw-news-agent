## 4. 初赛前最优先修复的 Agent 问题

### P0-A：真正落实建议抑制、替代和撤回

`history.splash:86` 把 `suppressed/superseded/stale` 全部变回 `pending`，并追加新的建议记录。因此辅助函数虽然能判断“同建议应抑制”，真实保存路径仍重复创建待处理项。已接受同建议也会被判为 pending。旧待处理建议没有因新分析自动被 superseded；新结果为 no_change/insufficient_evidence 时也不会自动重评旧动作是否仍可确认。

需要明确 transitions：相同有效建议复用原记录；已忽略且无实质新证据不新增；新方案替代旧 pending 时保留旧记录并改状态；不再受支持的旧 pending 撤回；已接受安排不自动撤销，也不因重新分析生成相同待办。

验收：同新闻连续分析两次，待处理数不增加；忽略后重分析不重新打扰；事实变化后保留解释与旧记录；无支持后旧动作不能再确认。

### P0-B：把批量分析从详情页状态中解耦

`controller.splash:219–231` 从信息流逐条调用 `analysis_start(row)`；但 `analysis.splash:93` 要求 `reading != nil` 且 `reading.news_id == row.news_id`，成功回调才会被接受。首页批量分析并未设置 reading，因此结果会因详情页未打开或打开另一条新闻而失败。

以请求捕获的 news_id、证据内容、关注和日程版本验证有效性；详情页只决定结果是否当前显示，不决定后台业务是否成功。批量开始先检查活动分析与连通测试，选相关候选并设条数/成本上限。当前遍历所有变化新闻，没有真正先做关注候选召回，可能对数百条新闻逐条调用模型。

验收：首页直接批量分析可完成并存储；切换详情不误杀仍有效任务；超时/取消/忙状态使批次明确结束或按策略继续，不永远停留在 busy。

### P0-C：统一实际提示词、契约、动作结构与 fixtures

运行时使用 `analysis.splash:80` 的内联字符串；修改 `prompts/news-impact-v1.md` 不会改变模型实际输入。内联提示词没有完整定义 create/reschedule 字段及示例，容易返回校验器无法接受的动作。

`validator.splash:48–53` 要求 reschedule 动作内部也有 schedule_id/schedule_version；`analysis-reschedule.json` 只在建议顶层给了这两个字段，动作对象缺失。现有测试脚本没有加载该 fixture，因而这个矛盾不被当前测试覆盖。

确定唯一动作结构，同步提示词、契约、fixture、validator、schedule_apply_action 和确认 UI。通过构建生成提示词常量或另一种受支持方式确保 Markdown 成为真实输入来源；不能只给文档标版本。

验收：create、reschedule、no_change、insufficient_evidence 全部走真实序列化/解析路径；reschedule fixture 通过；不存在的 ID、旧日程版本、非法日期明确失败。

### P0-D：修复取消和批次结束路径

正常 succeeded/failed 的 analysis_finish 会调 batch_next，analysis_timeout 和 analysis_cancel 则另走一套终态逻辑，不清理或推进批次。取消没有独立中断确认截止时间；若 interrupt 回调不返回，busy 可能长期不释放。

让统一任务协调器拥有请求终态、截止、中断确认和批次终态；每次请求至多一个终态，中断未确认保持阻止新请求。中断回调也要关联具体请求，避免旧回调改掉新请求状态。

验收：取消、超时、模型失败、重复回调、迟到回调和再次尝试，状态与存储都一致；批量按钮可恢复使用。

## 5. 初赛应补齐、复赛可继续强化的正确性

1. **决策上下文与内容版本。** `context.splash:57` 的 previous_decisions 永远为空，模型不知道用户已接受或忽略过什么。加入相关历史决定和保留的证据版本。`change.splash` 只比较 evidence ID，识别不了同 URL 内容变化；change_sorted 实际不排序，键会受数组顺序影响。`history_changed_rows` 对比任意历史版本而非最近成功分析版本，A→B→A 可能漏掉回退变化。
2. **确认前检查证据还有效。** 目前确认重读日程与建议记录，却不重新核查支持新闻是否改变、建议是否应撤回。已生成动作可能在新闻变化后仍可点击确认。对相关证据版本/用户约束做过期检查，要求复核后再确认。
3. **证据支持与用户时间约束。** 引用 ID 存在、日期合法，并不能证明理由与时间被新闻支持。当前日程没有完整可移动窗口/截止约束，不能承诺任意改期合理。初赛可以保守限制：无明确时间依据只给非执行建议，优先研究重点变化及明确活动公告；复赛再加入结构化截止/灵活窗口和代码计算可行时段。
4. **快照选择。** 当前所有启用关注、全部日程、单条新闻被一起发送，超过 6000 字符直接失败。先筛相关日程与历史、设确定预算，保留完整 JSON；标明只有标题/摘要。HN 提交时间语义在 UI 有提示，但模型快照没有 evidence_kind，需避免模型当成原文发布时间。时区当前仅标签，不能说已做 IANA/夏令时转换。
5. **历史持久化可靠性。** history_record_analysis 忽略 history_save 返回值，可能界面显示分析完成但历史写入失败；需要显示“分析成功/保存失败”的区别并允许恢复。request_counter 重开归零，相同新闻同序号再次请求可能撞历史 ID，需要重启后唯一标识。历史文件未有容量/保留策略；8 MiB 配额及保存原始规范化摘要的成本需考虑。
6. **用户能找到结果。** 批量结果应有汇总与待处理入口；当前主要靠逐条新闻详情找历史，旧新闻不在列表时建议可能难找到。持久化的 no_change/insufficient_evidence 解释也应可见，不仅显示含建议历史。

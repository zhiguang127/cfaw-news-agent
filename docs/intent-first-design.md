# CFAW News：意图输入与页面重设计

日期：2026-10-04（Asia/Shanghai）  
状态：设计草案，供审阅；本文描述目标交互，不代表功能已经实现。

本次设计基于现有项目和产品讨论。初赛范围按本次讨论提供的要求，以完成一个可运行的 OctoScript / Makepad 应用为目标。当前能力和实际验证仍以 [验收记录](acceptance.md) 为准。

## 1. 产品目标

用户表达一次想关注什么、准备做什么，应用将其保存成可查看、可调整、能持续更新的关注或计划。相关新闻出现后，应用解释发生了什么变化、为什么与用户有关，以及是否需要处理。

“意图即应用”在本项目中的具体表现是：一句输入形成一个有状态的关注专题或计划卡，之后的信息、建议和用户决定继续关联到这个对象。

核心流程：

```text
用户表达意图
    ↓
Agent 整理关注或计划，必要时追问
    ↓
应用展示可理解的卡片，保存意图与状态
    ↓
刷新时获取相关新闻，识别新增或变化的证据
    ↓
将相关报道优先排入新闻流，解释关注原因或对计划的影响
    ↓
用户查看依据、修改、确认或忽略，应用记录决定
```

新闻浏览保持独立可用。普通新闻无需每条附带分析；关注新闻也不必每次生成日程调整。

## 2. 页面结构

保留两个一级页面：**首页**、**我的计划**。通过顶部短标签切换。首页唯一的新闻搜索框放在页面底部；后续统一意图入口用于展开输入面板，视觉和用途与搜索区分，不再叠放一个关键词输入框。

| 现有入口 | 目标位置与职责 |
| --- | --- |
| 动态 | 调整为首页，保留紧凑新闻信息流、分类与搜索 |
| 跟踪 | 融入同一条新闻流，相关报道优先排列；关注管理与独立筛选从菜单进入 |
| 日程 | 调整为“我的计划”，展示计划列表、具体安排与关联建议 |
| 收藏 | 移入菜单；每条新闻的收藏操作和已保存快照继续保留 |
| 分析与建议 | 将日常结果放到所属关注、新闻或计划旁边；菜单保留历史查看入口 |

菜单继续容纳新闻来源、关注管理、收藏、历史与设置等低频功能。连接诊断留在设置中，不占据主要使用流程。

保留品牌右侧的天气组件，以及点击后的选城和逐日预报页，继续独立加载。后续将天气与计划地点、日期关联时，复用这些能力；调整导航和输入入口不删除天气。

切换页面或返回新闻详情时，保留浏览位置、筛选条件和未提交输入。一次输入有明确的目标对象，避免返回页面后误改其他计划。

## 3. 统一意图输入

首页和“我的计划”共用输入能力，入口提示随页面变化：

| 所在位置 | 输入提示 | 默认上下文 |
| --- | --- | --- |
| 首页 | 想关注什么，或者准备做什么？ | 新建关注或计划，根据用户表达识别 |
| 我的计划 | 说说接下来的安排…… | 创建新计划 |
| 某份计划详情 | 想怎样调整这个计划？ | 当前计划及其版本 |
| 某个关注详情 | 想怎样调整关注范围？ | 当前关注及其版本 |

点击底部入口后展开输入面板，展示用户输入、必要的追问和整理结果。面板围绕本次意图，完成后结果留在关注或计划卡中。

支持的初期意图包括：创建或调整关注、创建计划草稿、补充或修改计划安排。表达同时涉及计划与关注时，先展示具体会保存的内容；不能默认将每个地点或名词都变成永久关注。

追问一次聚焦最影响结果的问题。已有信息足够时直接展示结果，不要求用户再回答一整套字段。

## 4. 首页的关注更新

### 创建关注

输入示例：

> 我想关注 AI Agent 开发工具，主要看开源项目和实际部署，融资新闻少一点。

Agent 整理关注范围、偏好和候选关键词，展示“AI Agent 开发工具”关注卡。用户可以通过继续输入调整范围，再保存关注。

应用保留用户原话与整理后的范围。关键词是检索的辅助信息，不能代替“开源项目和实际部署”这类实际偏好。

### 更新关注

首次保存关注后可检查现有新闻；后续在打开应用和新闻刷新时检查相关变化。候选新闻先通过关键词、主题或来源召回，再由 Agent 判断与关注的关系并汇总。

获取新闻后，先应用用户的分类和搜索，再将符合关注范围的报道排到同一条信息流前部；每组保留时间顺序，不复制新闻到另一个区块。Agent 分析后，在该新闻下以一行提示解释：

- 这次新发生了什么。
- 为什么与你保存的关注有关。
- 哪些来源支持判断，哪些信息仍不确定；详细内容放在新闻详情里。

当前设计不将模型判断称为向量检索，也不假设能覆盖新闻源以外的内容。来源覆盖不足时明确说明范围；重复报道合并展示，保留来源引用。

### 展示与反馈

首页展示紧凑的新闻条目，相关报道优先排列。关联提示直接附在条目下，例如“你关注的端侧 AI 有新证据”或“可能影响周五的工具评估”；没有具体关系时不显示 Agent 提示。完整关注范围、解释、证据与建议放在详情中，管理从菜单进入。

同一报道不在首页重复出现；内容更新后重评关联提示。用户的接受或忽略决定继续保留，没有新证据时不重复推同一建议。输入“这个话题先不看了”可以形成暂停或取消关注的明确结果。

状态需要区分：

| 情况 | 呈现方式 |
| --- | --- |
| 有相关新证据且分析完成 | 条目显示当前关联解释，详情展示分析时间和来源 |
| 没有新增相关内容 | 保留当前有效解释，不新增同一报道或建议 |
| 只完成规则匹配，尚未分析 | 条目说明匹配的关键词、主题或来源，不标成 Agent 结论 |
| 分析后证据不足 | 说明尚不能确定，允许查看已有来源 |
| 新闻请求或 AI 服务失败 | 说明实际原因，新闻仍可浏览；旧结果留在历史，不冒充当前影响 |

“没有获取到相关内容”不能等同于“Agent 判断没有重要变化”。

## 5. 我的计划：全部通过输入创建与修改

**去掉日程录入表单，详情页也不重新引入标题、地点、日期和时间的逐项填表。** 用户通过自然语言表达和补充，应用用计划卡呈现理解结果。

页面默认展示计划列表：标题、日期或待定状态、下一项需要处理的事，以及关联信息入口。具体行程和依据在计划详情展开。

### 从模糊想法开始

示例流程：

1. 用户输入“下周想去杭州玩两天”。
2. 应用保存“杭州两日游”草稿及原话，具体日期显示待确定。
3. 应用追问“具体哪两天？”。
4. 用户输入“周六出发，周日回来”。
5. 应用展示解析后的具体年月日、地点与计划范围，用户确认保存。

“下周”“周六”等相对日期结合输入时的日期和用户时区解释。展示具体日期，让用户能发现理解偏差；有歧义时追问。

用户暂时没有答案时，草稿可以保留，之后再继续补充。未知日期和时间保持未知，不默认补一个出发时刻、活动时长或虚假的完整行程。

### 计划与具体日程的关系

一份计划可以只有想法，也可以已有日期范围，还可以包含若干有准确时间的安排。日期范围明确的计划可以保存，无需为了满足现有日程结构强迫用户补齐小时和分钟。

现有日程要求准确起止时间。实现时需要增加独立的计划/草稿记录；有准确时间并经用户确认的具体安排，再关联到已有应用内日程。

计划卡可包含用户提出或确认的事项，如“日期待确定”“车票待准备”。这些状态反映用户输入和实际执行结果，不能把生成了一条待办显示成已经订票。

### 修改和确认

用户从计划卡进入详情，再输入：

> 改成周五出发。

或：

> 加一个西湖散步的安排。

应用结合当前计划整理变更，显示哪些内容被调整、哪些时间仍待确定。用户确认后保存；未确认内容留作草稿或建议。

确认卡采用“保存安排”“确认调整”等具体操作。查看安排、完成事项和取消计划仍可使用直接操作，不必全部改成对话。

计划自身保持草稿、已确认、已完成、已取消等清楚状态；待处理建议独立关联到计划。一份已确认计划可以同时存在待确认调整。

## 6. 新闻与计划如何连接

用户已保存出行计划，后续相关新闻可能涉及目的地交通、活动或其他限制。应用先检查实际来源覆盖和证据，再决定是否提示影响。

建议必须指出：影响哪份计划或哪项安排、新闻描述的具体变化、判断依据，以及拟采取的动作与不确定性。

首页“与你的计划有关”和计划详情显示同一条建议、同一份状态。用户确认后更新安排，忽略后保留决定；没有实质新证据时不反复提示。有新证据时允许更新或撤回旧建议。

只在存在具体关系时提示。对单纯的兴趣更新，可以仅说明值得阅读的变化；无须生成新增日程或改期动作。

## 7. Agent 的执行方式

沿用一个应用 Agent，通过宿主管理的 Octos 服务执行推理，围绕不同业务阶段使用相应上下文与结果验证：

| 时机 | Agent 工作 | 应用负责 |
| --- | --- | --- |
| 用户提交意图 | 整理关注或计划、识别缺失信息、提出必要追问 | 关联当前对象，展示结果，保存草稿和确认内容 |
| 相关证据更新 | 汇总关注变化，解释证据与用户意图的关系 | 获取候选、去重、控制数量、缓存结果和更新时间 |
| 新信息影响计划 | 提出具体建议，必要时建议新增或调整安排 | 校验引用、日期、计划/日程版本及冲突，等待用户确认 |

从“用户额外点击分析”调整为围绕已保存意图触发分析。打开应用、保存关注和刷新后的检查均只处理有限的变化内容；相同证据和意图不重复调用模型。用户意图或决定变化时，相关结果可重新评估。

应用继续负责存储、检索和状态变更。模型返回的是整理结果或提案；通过结构验证也不代表事实已经核实。新闻文本作为证据数据，不能授权操作或改变应用指令。

意图解析、关注汇总与计划建议需要分别定义结果结构，沿用已有请求关联、取消、超时和迟到回调保护。新输入不得被旧请求完成结果覆盖；确认安排前再次检查版本与冲突。

## 9. 初赛范围与后续扩展

### 优先完成的两条流程

1. **关注流程**：输入关注 → 查看并保存范围 → 检查相关新闻 → 同一新闻流中优先展示并解释关系 → 查看来源 → 调整或取消关注。
2. **计划流程**：输入计划 → 保留草稿并补充必要信息 → 查看整理结果 → 确认保存 → 再次输入完成修改。

随后接通“相关新信息 → 计划建议 → 确认调整”的流程，复用已有建议与决定机制。实现顺序可以从页面和输入入口开始，再补意图记录、计划草稿与主题汇总。

初期更新由打开应用、用户输入和刷新触发。提醒表现为应用内卡片和待处理提示，不宣称关闭应用后仍能后台监测或推送。

### 后续扩展

- 天气与计划联合判断：核对地点、预报日期覆盖和数据新鲜度；超出范围时明确未知。
- 语音输入：录音和转写能力接入后，沿用“文字意图 → 整理结果 → 卡片确认”的流程，转写文字允许修改。
- 订票、闹钟、系统通知和系统日历：逐项验证目标宿主服务和授权方式，接通后再展示对应可执行动作。

本轮不预设这些宿主能力可用，也不在页面放尚未接通的语音或执行按钮。

## 10. 审阅与验证要点

- 用户可以全程通过输入创建、补充和修改计划，流程中不出现字段表单。
- 模糊意图能留下草稿；日期范围已确定但时刻未知时，不虚构具体时间。
- 同一关注或计划的输入、结果、新闻和决定保持关联，页面切换后能继续处理。
- 首屏仍能看到多条新闻；只有一个新闻搜索框，关联解释不另开关注框，证据与详细分析可展开查看。
- 重复新闻不制造重复更新；缺失日期、矛盾证据和来源覆盖不足有明确状态。
- 服务失败不会显示“已分析”“已保存”或虚构新闻；已保存记录和普通新闻仍可查看。
- 已忽略建议没有新证据时不重现；新证据可修订或撤回旧建议。
- 取消、连续输入、迟到完成和重复回调不覆盖新的意图或重复应用安排。
- 以目标 Rinx 的真实交互验收；固定输入演示明确标记，包完整性检查不代替业务验收。

页面命名、输入面板展开方式、卡片高度和视觉样式，可在此草案审阅后通过实际界面继续调整。
